# Workflow 核心契约

按风险缩放：Fast 合并阶段、不写文件；Standard 写 3–5 行计划；Critical 写显式契约。不是每次任务都写完整报告。

## 阶段表

| 阶段 | 动作 | 出口（可观察） | 失败返回 |
|---|---|---|---|
| Discover | 读适用规则、目标分支/环境、真实代码、现有能力；记录 baseline `git status` 与 HEAD；识别权限边界 | 能说出：改哪、谁负责、已有什么检查、什么不能碰 | 范围不清 → 向用户确认（仅当影响授权或不可逆决定） |
| Define | 目标、非目标、验收条件、约束、允许的副作用 | 验收条件可被命令/截图/状态转移判定 | 验收不可判定 → 重写为可观察结果 |
| Reproduce / Baseline | Bug 先复现并固化失败用例；性能先测基线；新功能定观察点 | 失败用例红 / 基线数据已存 | 复现不了 → 记录环境差异，标 BLOCKED，不凭猜修 |
| Design | 沿用现有架构取最小正确改动；Critical 补备选、不变量、回滚、独立挑战 | 方案与回滚路径写明；Critical 经过独立质疑 | 发现风险升级 → 升档 |
| Implement | 小步可回退；优先复用；diff 聚焦；不借题重构、不掩盖缺陷 | 变更集与方案一致 | 越界改动 → 拆出去或回退 |
| Verify | 快检 → 针对性测试 → 真实入口运行 → 按风险加回归/性能/安全/属性测试；结果绑定状态指纹 | `ewk check --require …` 通过 | 失败 → 回 Implement 或 Design；连续无进展 → 换诊断策略或报告阻塞 |
| Review | 按严重度审 diff 与证据；Critical 做独立/跨 Agent 验证 | 无未处理的 high；其余有处置 | 发现问题 → 回对应阶段 |
| Deliver | 变更清单、证据、风险、状态；需要 PR 调 `pr-authoring`；远程动作须授权 | 用户拿到可核对的交付报告 | 证据过期 → 重新 Verify |
| Learn | 只在有新发现时：补回归、修约束、更新现有能力 | 无新发现则不产出文档 | — |

## 状态

任务状态与检查状态分开记。词表：`PLANNED / IN_PROGRESS / PASS / FAIL / BLOCKED / NOT_RUN / NOT_APPLICABLE / PENDING`。旧有失败要给基线证据并说明影响，不能静默跳过。

## 多 Agent

默认一个负责人闭环。仅当：工作可独立拆分、确需不同视角、或 Critical 需要独立验证，才派其他 Agent；平台不支持时降级为单 Agent 分阶段并标注“非独立”。
子任务 brief 必须含：目标、允许修改的文件/目录、依赖、输入 SHA、验收、预算、返回格式。并行写入用隔离工作树或明确文件所有权。负责人负责集成与最终候选版本的完整验证；子 Agent 结论不是事实，其“已清理/已完成”须核对。
项目规则若允许更多并行（如项目手册明确许可），以项目规则为准，仍须文件所有权与负责人集成。

## 长任务与交接

最小状态：目标/非目标、base/head SHA、已完成证据（指向 evidence 文件）、未完成项、已试失败路径、下一步、阻塞、环境。新会话先恢复状态 → 查 `git status`/diff → 跑最小健康检查 → 再继续；换 commit/依赖/环境后只重验受影响部分。已有 `work-handoff` 或项目交接入口时用它，不另建。

## 预算与停止

按风险设时间/测试次数/并发上限，用于防失控，不用于压缩必要验证。同一失败连续两次未改变原因 → 停止重试，换诊断方法或报告 BLOCKED。禁止固定轮数的“多 Agent 评审”仪式；评审轮数由是否仍有新发现决定。

## 恢复与回滚

只回滚本次登记过的、哈希未漂移的文件；先保存现状与失败证据，再处理半完成回滚，最后才开新工作。部署类变更先备份旧版本与指纹，并验证回滚能恢复旧行为。
